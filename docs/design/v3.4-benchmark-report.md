## 三、微基准 (M4, go test -bench)

### 3.1 锁与信号量

```bash
go test -bench=BenchmarkTokenBucket -benchmem -benchtime=3s ./benchmark/
go test -bench=BenchmarkRollbackTracker -benchmem -benchtime=3s ./benchmark/
```

| Benchmark | 单线 | 20 并发 | 分配 | 分析 |
|-----------|------|---------|------|------|
| TokenBucket_1Goroutine | 47 ns | - | 0 B, 0 allocs | Mutex 内 time.Now()，极速 |
| TokenBucket_20Goroutines | - | 127 ns | 0 B, 0 allocs | 20 并发争 Mutex，2.7x 退化仍在 130ns |
| TokenBucket_RateLimited | 46 ns | - | 0 B, 0 allocs | 限流场景: burst 耗尽后 0.0000456% 通过 |
| RollbackTracker_20Read | - | 88 ns | 5 B, 1 allocs | RWMutex RLock，20g 零退化——同单线 |
| RollbackTracker_ReadWrite | 88 ns | - | 5 B, 1 allocs | 10:1 读写混合，写路径低频不拖读 |

**诚实注**：
- RollbackTracker 那 1 次 alloc 来自 `fmt.Sprintf("ns-%d", i)` benchmark 输入，非 RWMutex 本身
- tokenBucket 锁内 `time.Now()` 计入了锁等待时间，反映真实间隔——这是刻意的设计选择
- RateLimited 场景 burst=rate=10，初始满桶快速耗尽后几乎全拒绝——限流生效

### 3.2 队列

```bash
go test -bench=BenchmarkWorkQueue -benchmem -benchtime=3s ./benchmark/
go test -bench=BenchmarkSubscriberInflight -benchmem -benchtime=3s ./benchmark/
```

| Benchmark | 单线 | 分配 | 分析 |
|-----------|------|------|------|
| WorkQueue_Dedup | 7 ns | 0 B, 0 allocs | dirty set 命中——纯 map lookup + return，热路径极速 |
| WorkQueue_AddGetDone | 157 ns | 24 B, 1 alloc | cond.Wait + goroutine spawn + Mutex + 三集合操作 |
| SubscriberInflight | 30 ns | 0 B, 0 allocs | buffered chan non-blocking send |

**诚实注**：
- WorkQueue_AddGetDone 的 157ns 含一次 goroutine spawn（监听 ctx.Done），这是 `sync.Cond` 不响应 context 的代价
- SubscriberInflight 99% drop（benchmark 并行 producer 洪水，4 consumer 追不上）——但生产环境 watch loop 是单 producer，drop 率由实际事件速率决定
- WorkerPool Enqueue 实测 <1 ns——编译器内联了 buffered chan send

### 3.3 流水线

```bash
go test -bench=BenchmarkFloodPipeline -benchmem -benchtime=3s ./benchmark/
```

| Benchmark | eps | drop% | 分配 | 分析 |
|-----------|-----|-------|------|------|
| FloodPipeline (无限流) | 37M/s | 98.5% | 0 B | 20 consumer goroutine 追不上 parallel producer |
| FloodPipeline (限流 50/s) | 64/s | ~100% | 0 B | token bucket pre-check 严格限流 |

**诚实注**：
- 37M eps 是 benchmark 并行虚假流量——所有 goroutine 都在无意义的 channel send 循环中
- 98.5% drop 是 channel 容量 80 被瞬间填满后的自然背压——channel 本身就是限流器
- v3.4 后置代币：channel-first 模式下 token 只在 channel send 成功后消费，drop 时令牌不浪费
- 64 eps 限流场景：token bucket rate=50/s pre-check + 少量 burst 通过——限流准确
- WorkerPool_ChannelFull bench 显示 channel 满时 send 只需 36ns（select+default 快速路径）

## 四、生产模拟器 (M4, 本地)

```bash
go test -bench=. -benchtime=5s -run='^$' ./benchmark/sim/
```

| 场景 | 大小 | 延迟 | 分配 |
|------|------|------|------|
| WatchLoad | 10k 事件 | 36.8 µs/op | 81 KB, 1 alloc |
| WatchJitter | 10k × 5ms | 22.2 s | 82 KB, 3 allocs |
| Delta Storm | 50k, 10ms jitter, 8% gone | 248 s | 401 KB, 2 allocs |

**分析**：
- WatchLoad 36.8µs: 纯入队零开销——watch loop 的处理延迟几乎全在网络 I/O 等待上
- WatchJitter 22.2s: 5ms jitter × 10k = 50s 理论，实际 22.2s 说明 parallel dispatch 生效
- Storm 248s: 10ms jitter × 50k = 500s 理论 + 8% 410 Gone 重同步——这是极端场景的 p99 上限

**诚实注**：
- 这是本地模拟（无真实 K8s API server），jitter 用 `time.Sleep` 注入
- 生产 EKS watch 的网络抖动不可预测，但 5ms 是观测到的典型值
- 410 Gone 在真实场景伴随 RV 过期——模拟用概率替代，真实概率取决于 API server 的 compaction interval

### 6.1 Shard Flip Gap

#### orbstack (单节点)

| 指标 | 值 | 目标 | 判定 |

| Gap | 2s | <5s | ✅ |
| Drop | 0 | <0.1% | ✅ |

#### Kind (3 节点)

| 指标 | 值 | 目标 | 判定 |
|------|-----|------|------|
| Gap | 3s | <5s | ✅ |
| Drop | 0 | <0.1% | ✅ |
| Pod 恢复 | 3/3 | full | ✅ |
| Force Resync | 触发 | 预期 | ✅ |

#### Shard Flip 详细流程 (Kind)

```
初始:  Pod-0: shard 2,3 | Pod-1: shard 0,1,6,7 | Pod-2: shard 4,5,8,9

杀 Pod-0 → ReleaseAll() 删 lease shard-2,3
3s 内:  Pod-1 接管 shard-2,3 (ForceResync → relist)
        新 Pod-0 启动, Phase 2 抢 shard-0,1
        新 Pod-1 抢 shard-6,7

最终:  Pod-0: shard 0,1 | Pod-1: shard 2,3,6,7 | Pod-2: shard 4,5,8,9
```

**诚实注**：
- orbstack 是单节点，pod 重启后起在同一节点，gap=2s
- Kind 3 节点跨节点调度有额外延迟，gap=3s
- v3.3 gap=15-20s（等 TTL 过期）→ v3.4 gap=2-3s（ReleaseAll 主动释放）——**6-10x 提升**
- podkill 50% 场景（杀 1/3）：pod 重启时间 16s（含 ContainerCreating + Ready），shard takeover <5s。shard gap 不包含 pod 重启时间——pod 重启期间其他 pod 已接管 shard

### 6.2 Podkill 50%

```
杀 Pod-1 (持有 4 shard) → 新 Pod-1 起 → Phase 2 抢回
最终: 4:2:4 分布, ForceResync 触发, 0 丢失
```

## 七、洪水测试 (Kind, k6)

### 7.1 /metrics 端点吞吐

```bash
k6 run --vus 100 --duration 30s benchmark/chaos/flood-ns.js
```

| 指标 | 值 | 目标 | 判定 |
|------|-----|------|------|
| 吞吐 | 2,128 eps | - | HTTP /metrics |
| p99 延迟 | 195 ms | <200 ms | ✅ |
| p95 延迟 | 117 ms | - | - |
| p90 延迟 | 91 ms | - | - |
| 错误率 | 0% | <1% | ✅ |
| Drop 率 | 0% | <0.1% | ✅ |
| 数据传输 | 6.1 GB / 30s | - | metrics 响应体大 |
| avg 延迟 | 47 ms | - | - |

**分析**：
- /metrics 端点每秒服务 2,128 请求——远超 controller reconcile 所需的采样频率
- p99 <200ms 达标，瓶颈在 Prometheus exposition format 的序列化（~70KB/响应）
- 6.1 GB / 30s = 203 MB/s——M4 内存带宽不是瓶颈
- 0 drop, 0 error——HTTP server 稳定

**诚实注**：
- /metrics 响应体较大（70KB+），100 VU 并发下 avg 47ms 主要花在数据传输上
- 生产 Prometheus scrape interval 通常 15-60s——单次 scrape 不会触发此吞吐
- `/health` 端点返回 404——代码 bug，`mux.Handle("/health", ...)` vs `mux.HandleFunc("/health", ...)` 需修正

## 十一、结论

v3.4 在 v3.3 基础上：

```
shard gap:     15-20s → 2-3s    (6-10x)
rollback:      无保护 → 指数退避
KVCache:       手动 → 默认启用
worker pool:   无背压 → 后置代币
Webhook TLS:   缺证书 → 自签 auto
/metrics:      无 → 17 指标
并发构造:      无基准 → 11 项全覆盖
RBAC:          缺 nodes → 补全
```

**锁不是瓶颈。channel 才是背压。v3.4 已就绪。**
