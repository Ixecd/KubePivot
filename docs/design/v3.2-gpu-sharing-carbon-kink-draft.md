## 一、目标

v3.1 解决"怎么把 GPU 卡分下去"。v3.2 解决三个上层问题：

1. **空间维度**：一张卡别浪费。MPS/MIG/TimeSlicing 把 GPU 利用率从 40% 推到 85%+
2. **时间维度**：非紧急 Job 别在脏电时段跑。碳感知调度把碳排降到合理水平
3. **测试维度**：没有 8×A100 也能验证拓扑调度。KinK 模拟上万个 fake 节点压测乾枢

## 二、空间维度：GPU 共享

### 2.1 解决什么问题

v3.1 整卡调度下，一个推理 Pod 申请 1 张 A100 跑一个 batch_size=1 的小模型，GPU 利用率 < 30%。剩下 70% 的算力被浪费。GPU 共享让多个推理 Pod 共用一张卡，把闲置算力用起来。

### 2.2 三种共享模式

| 模式 | 粒度 | 适用场景 | 复杂度 |
|---|---|---|---|
| **MPS** | 逻辑算力 (0.1 GPU) | 多推理 Pod，同 CUDA context | 中 |
| **TimeSlicing** | 时间轮转 (50ms 切片) | 开发测试，延迟不敏感 | 低 |
| **MIG** | 硬件分区 (1g.5gb) | 不同模型需要硬件隔离 | 高 |

#### MPS（Multi-Process Service）

NVIDIA 驱动层的多进程共享。多个推理 Pod 共享同一个 CUDA context，GPU 硬件层面做指令流并发。

**KubePivot 实现要点**：

```go
// sizing/dp.go — RecommendedGPU 从 int → float64
type Suggestion struct {
    RecommendedGPUCount float64 // v3.2: 0.1 粒度，如 0.2 = 20% GPU
    RecommendedGPUMem   int64
    SharingMode         string  // "mps" | "timeslicing" | "mig" | "exclusive"
}
```

```go
// bin_pack.go — MPS 并发限制
const maxMPSPerGPU = 48  // A100 最大 48 个 MPS client

func (n *NodeInfo) AvailableMPS() int {
    allocated := 0
    for _, pod := range n.AssignedPods {
        if pod.SharingMode == "mps" {
            allocated++
        }
    }
    return maxMPSPerGPU - allocated
}
```

**约束**：MPS 要求所有共享 Pod 运行同一 CUDA 版本。不同 CUDA 版本的 Pod 不能共享同一张卡。

#### TimeSlicing

本质是资源超卖（Overcommit）——允许多个 Pod 的时间片 sum > 1 GPU，按 priority 排队执行。coordinator 像处理 CPU soft limit 一样处理。

**KubePivot 实现要点**：

```go
// coordinator.go — TimeSlicing 超卖检查
func (c *Coordinator) checkTimeSlicingOvercommit(node *NodeInfo) bool {
    sum := 0.0
    for _, pod := range node.AssignedPods {
        if pod.SharingMode == "timeslicing" {
            sum += pod.Requests.GPU
        }
    }
    // 允许 3x 超卖（最多 3 个时间片 Pod 共享一张卡）
    return sum <= 3.0
}
```

#### MIG Auto-Config（核心突破）

这是 KubePivot 首次具备"写硬件"能力——根据 `resources.yaml` 动态重组 GPU 分区。

一张 A100-40GB 可以切成：
- 7× 1g.5gb（每个 5GB 显存）
- 3× 2g.10gb + 2× 1g.5gb
- 1× 4g.20gb + 1× 2g.10gb + 1× 1g.5gb
- ...（7 种组合）

```yaml
resources:
  - name: llama-inference
    gpu:
      count: 0.2          # 逻辑 GPU 份额
      sharingMode: mig
      migProfile: 1g.5gb  # 具体 MIG 分区
```

**实现路径**：KubePivot 通过 `nvidia-smi mig` 命令或 nvidia-mig-manager API 动态创建/删除 MIG 设备。执行前需要确认节点上没有正在运行的 Pod 使用该 GPU（安全窗口）。

### 2.3 resources.yaml 共享配置

```yaml
resources:
  - name: model-inference
    kind: Deployment
    gpu:
      count: 0.3                    # v3.2: 浮点数 GPU 份额
      product: A100-SXM4-40GB
      sharingMode: mps              # mps | timeslicing | mig | exclusive(v3.1)
      migProfile: ""                # MIG 模式时指定分区大小
    schedulingPolicy:
      sharingIsolation: soft        # soft: 允许超卖 / hard: 严格隔离
```

## 三、时间维度：碳感知调度

### 3.1 解决什么问题

一个训练 Job 下午 3 点跑和凌晨 3 点跑，计算结果是完全一样的。但下午 3 点电网的碳排放强度可能比凌晨高 30%（化石能源占比更高）。碳感知调度把非紧急 Job 自动延迟到低碳窗口，在不影响产出的前提下降碳。

### 3.2 调度成本函数扩展

```
v3.0/v3.1: Cost = w₁·CPU + w₂·Mem + w₃·GPU
v3.2:      Cost = (w₁·CPU + w₂·Mem + w₃·GPU) × CarbonIntensity(t)
```

`CarbonIntensity(t)` 是时间 t 时刻电网碳排放强度（gCO₂eq/kWh）。凌晨 3 点可能是 200，下午 3 点可能是 400。

### 3.3 数据源

```go
// internal/metrics/carbon.go

type CarbonIntensityProvider interface {
    // GetCurrentIntensity 返回当前时刻的碳强度 (gCO₂eq/kWh)
    GetCurrentIntensity(ctx context.Context, region string) (float64, error)
    // GetForecast 返回未来 N 小时的碳强度预测
    GetForecast(ctx context.Context, region string, hours int) ([]CarbonPoint, error)
}

type CarbonPoint struct {
    Timestamp time.Time
    Intensity float64 // gCO₂eq/kWh
}
```

**数据源选择**：

| 来源 | 覆盖 | 延迟 | 费用 |
|---|---|---|---|
| WattTime API | 全球 | 5min | 免费配额 |
| Carbon SDK | 全球 | 实时 | 免费 |
| ElectricityMap | 欧/美/亚太 | 1h | 付费 |

KubePivot 先对接 Carbon SDK（免费 + 覆盖全球），后续扩展到 WattTime/ElectricityMap。

### 3.4 Coordinator 碳感知逻辑

```go
// scheduler/coordinator.go

type CarbonAwareConfig struct {
    Enabled         bool
    MaxDelayHours   int     // 最大延迟小时数（默认 12h）
    IntensityThreshold float64 // 碳强度阈值，超过此值才延迟
    Region          string  // 电网区域代码
}

func (c *Coordinator) scheduleWithCarbon(ctx context.Context, job *Job) (*ScheduleResult, error) {
    if !c.carbonCfg.Enabled || job.SchedulingPolicy.CarbonSensitivity == "None" {
        return c.scheduleImmediate(ctx, job) // 不受碳约束
    }

    current, _ := c.carbonProvider.GetCurrentIntensity(ctx, c.carbonCfg.Region)

    if current < c.carbonCfg.IntensityThreshold {
        return c.scheduleImmediate(ctx, job) // 当前碳强度低，直接跑
    }

    // 当前碳强度高 → 查找未来的低碳窗口
    forecast, _ := c.carbonProvider.GetForecast(ctx, c.carbonCfg.Region, c.carbonCfg.MaxDelayHours)
    for _, point := range forecast {
        if point.Intensity < c.carbonCfg.IntensityThreshold {
            // 找到低碳窗口 → 延迟到该时刻
            delay := time.Until(point.Timestamp)
            if delay > time.Duration(c.carbonCfg.MaxDelayHours)*time.Hour {
                continue // 超过最大延迟，放弃
            }
            return c.scheduleDelayed(ctx, job, point.Timestamp), nil
        }
    }

    // 未来 N 小时都没有低碳窗口 → 按原计划调度
    return c.scheduleImmediate(ctx, job), nil
}
```

**延迟上限**：每个 Job 通过 `resources.yaml` 声明自己能接受的最大延迟。非紧急训练 Job 可以接受 12h 延迟，紧急推理 Job 不接受延迟。

### 3.5 Waiting Queue

`coordinator` 维护一个优先级队列，被延迟的 Job 按 `(scheduledTime, priority)` 排序：

```
Waiting Queue:
  train-bert      → 2026-05-03T03:00:00Z (延迟到凌晨低碳窗口)
  train-gpt       → 2026-05-03T03:30:00Z
  finetune-llama  → 2026-05-03T04:00:00Z
```

到达 `scheduledTime` 时 coordinator 自动触发 Job 的 Pre-run 阶段。

### 3.6 resources.yaml 碳感知配置

```yaml
resources:
  - name: train-bert
    kind: Job
    gpu:
      count: 4
      product: A100-SXM4-40GB
      sharingMode: exclusive
    schedulingPolicy:
      carbonSensitivity: High    # High | Medium | Low | None
      maxCarbonDelay: 12h        # 最大延迟
      carbonRegion: US-West      # 电网区域
```

## 四、测试维度：KinK 加速

### 4.1 解决什么问题

v3.2 的 GPU 共享 + NVLink 拓扑碎片评分 + 碳感知延迟调度组合起来，逻辑复杂度爆炸。单机单元测试无法覆盖以下场景：

- 1000 个推理 Pod 请求 MPS 共享，分布到 128 张 A100 上，MPS client 数触及上限
- NVLink 拓扑碎片随时间累积，GPUNodeScore 是否正确地让拓扑友好的节点优先
- 碳感知调度在高强度时段将 200 个 Job 收集到 Waiting Queue，低碳窗口来临时批量触发

需要**不需要真实 GPU 集群**的端到端压测方案。

### 4.2 KinK 是什么

KinK = K8s in K8s。在 K8s 集群内部署一个 fake K8s API Server + fake Kubelet，模拟 N 个节点（含 GPU 标注）+ M 个 Pod。乾枢调度器不知道这些节点和 Pod 是假的——它们通过标准 K8s API 交互。

```
┌────────────────── K8s 集群 (真实) ──────────────────┐
│                                                       │
│  ┌─ Pod: kink-apiserver ───────────────────────────┐ │
│  │  Fake K8s API: /api/v1/nodes /api/v1/pods       │ │
│  │  └─ fake-node-0: 8×A100, NVSwitch topology      │ │
│  │  └─ fake-node-1: 8×A100, ...                    │ │
│  │  └─ fake-node-9999: 4×V100                      │ │
│  └──────────────────────────────────────────────────┘ │
│                                                       │
│  ┌─ Pod: kp-scheduler ─────────────────────────────┐ │
│  │  乾枢调度器，连接 kink-apiserver, 不知真假       │ │
│  │  └─ BinPack: 10000 nodes × 50000 pods           │ │
│  │  └─ Coordinator: GPUNodeScore × MPS limit        │ │
│  │  └─ Rescheduler: carbon-aware delay queue        │ │
│  └──────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────┘
```

### 4.3 两层 KinK

**第一层：压测层（v3.2a）**

模拟 10000+ fake 节点 + 50000+ fake Pod，验证乾枢调度器的计算性能：

- BinPack 在 10000 GPU 节点上的 FFD + DP 求解时间 < 5s
- GPUNodeScore 评分分布是否符合预期
- MPS client 上限约束是否正确触发
- 单次调度周期内存 < 2GB

**第二层：多租户隔离层（v3.2b）**

每个租户一个嵌套 K8s 控制面（类似 vcluster），KubePivot 作为外层调度器管理这些虚拟集群：

- 租户 A：CPU-only，100 个 fake 节点，2000 个 fake Pod
- 租户 B：GPU 密集，50 个 fake GPU 节点，500 个 fake Pod
- KubePivot 的 IAM 在租户间做权限隔离

### 4.4 Fake GPU 节点生成

```go
// internal/kink/gpu_fake.go

type FakeGPUCluster struct {
    Nodes         int
    GPUsPerNode   int
    GPUProduct    string      // "A100-SXM4-40GB"
    NVSwitchCount int         // 每个节点几个 NVSwitch domain
    TopologyFrag  float64     // 0-1, 拓扑碎片化程度 (0=完美, 1=全碎)
}

func (c *FakeGPUCluster) Generate() ([]*FakeNode, []*FakePod) {
    nodes := make([]*FakeNode, c.Nodes)
    for i := range nodes {
        nodes[i] = &FakeNode{
            Name:    fmt.Sprintf("fake-gpu-node-%d", i),
            GPUProduct: c.GPUProduct,
            GPUs:    make([]FakeGPU, c.GPUsPerNode),
        }
        // 按 TopologyFrag 决定 NVLink 拓扑的碎片程度
        for j := range nodes[i].GPUs {
            nvswitch := j / (c.GPUsPerNode / c.NVSwitchCount)
            if rand.Float64() < c.TopologyFrag {
                nvswitch = rand.Intn(c.NVSwitchCount) // 随机打散
            }
            nodes[i].GPUs[j] = FakeGPU{
                Index:    j,
                NVSwitch: nvswitch,
            }
        }
    }
    return nodes, generateFakePods(c.Nodes * c.GPUsPerNode)
}
```

**关键能力**：通过 `TopologyFrag` 参数控制 NVLink 拓扑的碎片程度，验证 GPUNodeScore 在不同碎片级别下的评分分布——这是真实集群上极难重现的场景（你不能在生产集群上刻意打碎 NVLink 拓扑来测调度器）。

### 4.5 KinK 的工程位置

KinK 不是 KubePivot 的 runtime 组件——它是 `tools/` 下的测试工具，与 `tools/scheduler_test/` 和 `tools/audit/` 同级：

```
tools/kink/
├── main.go              # 启动 fake K8s API Server + fake nodes + fake pods
├── gpu_fake.go          # GPU 节点 + NVLink 拓扑模拟
├── carbon_fake.go       # 碳强度时间序列模拟
├── stress.go            # 压测场景编排
└── README.md
```

**二进制体积**：KinK 独立编译（`go build -o kink tools/kink/main.go`），不打入 `kp` 二进制。`kp` 保持 ~30MB。
