Quantity 自实现 K8s 资源量解析（0 client-go）:

  哲学：保持 KubePivot "0 client-go" 哲学
  实现：自实现 parseCPU / parseMemory + 单位映射
  
  公式：Value = Base × Multiplier
    CPU 基准    = milli-cores (1 core = 1000m)
    Memory 基准 = bytes
  
  CPU 单位映射:
    ""  → 1000  (无单位 = cores)
    "m" → 1     (milli-cores)
    "k" → 1e6
    "M" → 1e9
    "G" → 1e12
  
  Memory 单位映射 (SI vs 二进制 - 关键区分):
    SI 10 进制:    "K"=1e3 / "M"=1e6 / "G"=1e9 / "T"=1e12 / "P"=1e15
    二进制 2 进制: "Ki"=1024 / "Mi"=2^20 / "Gi"=2^30 / "Ti"=2^40 / "Pi"=2^50
  
  例：
    "1G"  = 1,000,000,000 bytes (SI)
    "1Gi" = 1,073,741,824 bytes (binary)
  
  支持小数（生产数据兼容）:
    "1.5Gi" = 1,610,612,736 bytes
    "0.5"   = 500 milli-cores
  
  splitBaseUnit 算法：
    从右向左扫描，找第一个非字母位置
    支持单字母 (m/k/G) 和双字母 (Mi/Gi) 单位

KubectlMetricsClient 实现:

  调用模式：kubectl top pod/node -o json
  
  优势:
    - 几乎所有 K8s 集群都有 metrics-server (兜底)
    - 0 额外配置（依赖 kubeconfig 已有）
    - 0 额外依赖
  
  限制:
    - 仅当前快照（无历史）
    - 采样窗口由 metrics-server 控制（默认 30s）
    - 单次 ~100ms（kubectl fork 开销）
  
  错误处理:
    "NotFound" / "not found" → ErrNotFound (errors.Is 友好)
    其他 error → 包装原 error + truncated output

可测试性设计 (kubectl func 注入):

  问题：KubePivot executor 是具体单例 *KpExecutor，无 SetExecutor / Executor interface
        无法直接 mock executor.GetExecutor() 调用
  
  方案：函数变量注入 (与项目既有模式一致)
    type KubectlMetricsClient struct {
        kubeconfig string
        kubectl    func(ctx, kubeconfig, args...) ([]byte, error)
    }
    
    生产时：默认 = executor.GetExecutor().Kubectl (NewKubectlMetricsClient 内绑定)
    测试时：替换 client.kubectl = mockFn
  
  与既有模式一致:
    internal/eventstream/auth.go         readTokenFile / readCAFile
    internal/controller/informer_pool.go newInformerFunc
    internal/metrics/kubectl.go          kubectl  ← 本 commit

  测试哲学一致 (KubePivot 风格):
    在接口层 mock，不在 executor 层 mock
    既有 controller_test.go ~75 cases 验证此模式
