设计动机：

  v2.5 sharding.ShardSet 实际签名：
    func (s *ShardSet) OwnsNamespace(namespace string, totalShards int) bool

  eventstream.ShardSet 接口期望：
    Owns(namespace string) bool

  差异：v2.5 是无状态分片索引集合（需传 totalShards）
        eventstream 期望封装好的接口（只问 Owns）
  
  Adapter 桥接两者，并避免 internal/eventstream/ 直接 import
  internal/sharding/（保持依赖单向，仅此 adapter 文件做桥）

adapter_sharding.go 核心组件：

  shardSetAdapter struct:
    inner       *sharding.ShardSet  v2.5 类型借用引用
    totalShards int                  启动时一次性配置
  
  NewShardSetAdapter(inner, totalShards) ShardSet
    - inner=nil       -> 返回 nil（优雅降级）
    - totalShards<=0  -> 返回 nil
    - 否则封装为 ShardSet 接口
  
  Owns(ns) -> 转发 v2.5 的 OwnsNamespace
    hash 算法（FNV-1a 32-bit）由 v2.5 提供，不重复计算
    并发安全由 sharding.ShardSet 内部 RWMutex 保证

  staticShardSet struct:
    用于测试 / 单 pod 场景的固定 shard 实现
    不依赖 v2.5 sharding
  
  NewStaticShardSet(namespaces []string) ShardSet
    - nil 或空 slice -> 所有 ns 都归本 pod（单 pod 场景）
    - 非空 slice     -> 仅这些 ns 归本 pod（明确指定）

设计决策（A 路径锁定）：

  问题：adapter 如何处理 totalShards？
  
  A. 持有静态配置（启动时一次传入）          ← 选择
  B. 从 MultiLeaseManager 动态读
  
  数据：v2.5 的 m.totalShards 是私有字段（小写）
        没有公开的 TotalShards() 方法
        → B 路径不可行
  
  本质：v2.5 的 totalShards 是部署时配置（默认 10）
        改 totalShards 通常意味着滚动升级
        滚动升级时所有 informer 都会重建
        → "totalShards 不变" 是合理假设
  
  → A 简单、清晰、符合 v2.5 实际语义

OnShardChanged 回调的处理：

  v2.5 的 MultiLeaseConfig 已含 OnShardChanged 回调:
    OnShardChanged func(added, removed []int)
  
  v2.7.0 当前实现：adapter 不订阅此 callback
    shard 变化时漏事件，由 resync ticker（默认 30min）周期性兜底
    
  v2.7.1+ 计划：在 adapter 内启动 goroutine 监听 OnShardChanged
    新接管的 shard 对应 ns 触发 EventResync 补发对象
    实现复杂度高，YAGNI 暂不做
  
  注释中已记录此扩展点位置
