设计核心 (基准公平性原则):

  Bench 3 与 Bench 1/2/4/5 完全同公平赛道:
    - 不引入 envtest/真实 K8s API server (避免网络栈和 API server
      开销掩盖核心逻辑差异)
    - 不引入新依赖 (重用 SkeletonCache + ParseSkeleton)
    - 共享 generateComplexDeployment 测试数据 (1 客观数据集)
    - 同样 GOGC=200 / GOMEMLIMIT=4GiB / GOMAXPROCS=4 公平基准

  测试模型 (reflector watch loop hot path):
    client-go: json.Unmarshal(*Deployment) + Indexer.Update()
    KubePivot: ParseSkeleton + SkeletonCache.Put()
  
  两侧都是"接收到 watch event → 解析 → 写 cache"这一闭环
  测的是处理引擎对处理引擎，不是端到端。

测试矩阵 (8 个测试):

  Benchmarks (b.N 自动 / 固定批次):
    BenchmarkWatchThroughput_ClientGo            单事件
    BenchmarkWatchThroughput_KubePivot           单事件
    BenchmarkWatchThroughput_ClientGo_1000Events 批 1000
    BenchmarkWatchThroughput_KubePivot_1000Events
    BenchmarkWatchThroughput_ClientGo_10000Events 批 10000 (稳态)

  Tests (输出对比报告):

数据解读:

  1. 期望 "持平或微胜" → 实际 1.65-2.97x 提升 (超出预期)
  
  2. 内存维度提升更出彩 (allocs 降低 5.4x):
     client-go 反序列化整个 *Deployment 产生 517 个临时对象/event
     KubePivot ParseSkeleton 仅解关键字段，仅 96 个对象/event
     → 这是 Bench 5 (内存放大率) 差异的根因
     → Bench 3 + Bench 5 数据互相印证
  
  3. ROADMAP §5 验收:
     "全量重同步耗时 < 5s"
     1000 events ≈ 36ms 远低于 5s ✓
     10000 events ≈ 382ms 远低于 5s ✓
     验收通过
  
  4. 数据稳定性:
     单事件 σ < 5%
     1000  σ < 5%
     10000 σ < 10%
     → 测试基准合理稳定

工程意义:

  v2.7 自研 informer 路径数据驱动验证:
    Bench 1 (Cache Get):       预期 5-10x  → 待数据
    Bench 2 (Cache List):      预期 5-10x  → 待数据
    Bench 3 (Watch Throughput): 预期持平   → 实际 1.65-2.97x ✓ 超预期
    Bench 4 (Cold Start):      预期 2-3x   → 待数据
    Bench 5 (Memory):          预期 2x+    → 已验证

  Bench 3 数据强化了 v2.7 核心论断:
    "KubePivot 自研路径不仅 cache 读延迟低，
     watch 处理也明显领先，且内存效率 3-5x 提升。
     这是 client-go 反序列化整个对象架构的固有代价，
     不是优化 cache 数据结构能解决的。"
