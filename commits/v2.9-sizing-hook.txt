工程纪律亮点 (本次迭代的对齐实践):

  ✊ Cross-check 先行，不凭记忆写代码:
    - 写 hook 前 grep 确认: 
      • planner.Component 的 CPU/Memory 是 string 类型
      • yaml.v3 Marshal 输出格式 (无引号)
      • state.Machine.Transition 是单向的，重复调用会失败
    - 多花 10 分钟 grep，省 30 分钟 debug + 返工
    
  ✊ 为业务写测试，不为覆盖率写代码:
    - 测试验证业务语义 (c.CPU == "500m")，不验证序列化细节 (引号/缩进)
    - 3 个测试覆盖核心路径 + 关键边界，73.9% 覆盖率足够
    - 测试是保险丝 + 文档，不是数字游戏
    
  ✊ 真实结构对齐，不假设不猜测:
    - yaml.Marshal 输出 cpu: 500m (无引号) → 测试解析 YAML 后断言字段值
    - state.Machine 状态转换是单向的 → 删除重复的 Transition 调用
    - 每次写代码前: grep type/func/field, 看既有测试模式
    
  ✊ 最小必要原则，拒绝过度工程:
    - 单 Pod 优化 + 硬编码采样参数 (5 次/2s)，先跑通逻辑
    - 原子写入用 os.Rename 临时文件，不提前加备份/回滚
    - 错误处理用简单字符串匹配，不引入复杂错误类型

打脸预防 (基于本次迭代的教训):

  ✓ 第 1 次: 假设 yaml.Marshal 输出带引号 → 实际不带 → 测试匹配失败
    对策: 测试解析输出 YAML 后断言字段值，不匹配原始字符串格式
    
  ✓ 第 2 次: 重复调用 sm.Transition → 状态机拒绝二次转换 → 部署失败
    对策: 写状态机逻辑前 grep 确认合法转换路径，或用注释标注单向性
    
  ✓ 第 3 次: 自定义 contains 函数与 release_test.go 重复 → 编译错误
    对策: 优先用标准库 (strings.Contains)，避免跨文件重复定义辅助函数
