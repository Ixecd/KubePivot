v2.6.0 traffic-layer 的延续工作。把"已验证的流量配置"纳入
K8s 原生的状态广播机制——不引入新基础设施，复用 ConfigMap +
label 约定。

核心论断：
  "verified-traffic ConfigMap 是 K8s 原生的状态广播"
  
  kp deploy --env prod --from-env staging
  不是简单的"配置拷贝"，是三方协作的事件传播链：
    Staging Controller (生产者) - watch state → RUNNING + 5min
                                 → write ConfigMap
    kp 进程 (搬运工)             - 用户意图驱动的"主动拷贝"
    Prod Controller (消费者)     - 接收 sandbox commit + 走完整状态机

级联语义：
  传播链可任意级联 (staging → prod → DR-cluster → ...)
  任何 RUNNING + 5min 稳态的 env 都能作为传播源
  这是单一职责解耦的直接推论：三方都不知道彼此

16 个设计 Q 拍板：

  原始 8 个 (qc 独立拍板):
    Q1=ConfigMap+label    Q2=B 5min稳态     Q3=A 直连+KPEnv复用
    Q4=C 单集群+预留      Q5=C 直接覆盖     Q6=A 走蓝绿切换
    Q7=A fail-fast        Q8=A fail-fast
  
  cross-check 校准 3 项:
    Q1.1=A 一ns一cm       Q2.1=B 不改schema    Q6.1=C 不动git
  
  实施期补 3 项:
    Q9=A 进LOCKED之前读   Q10=A controller周期扫描   Q11=C 错误hint
  
  最后一档校准 4 项:
    1. RunningSince 不排除回滚后 RUNNING (writer 写实际状态)
    2. 是否更新判定: 对比 K8s 实际 vs ConfigMap data
    3. 测试矩阵: 单集群多 ns 已验证 + 多集群"未验证"诚实标注
    4. ConfigMap schema: traffic.yaml + source.yaml 双文件

设计原则 (沿 v2.6.0 哲学):
  - 不引入新基础设施 (复用 ConfigMap + label)
  - 复用 KPEnv 机制 (不发明新 kubeconfig 加载层)
  - 三方协作 / 单一职责
  - fail-fast 默认 (Q7/Q8/Q11 联合)
  - 不动 git (传播 ≠ GitOps 同步)
