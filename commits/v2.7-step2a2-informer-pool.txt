设计核心（双保险 + 添加而非嵌入）:

  InformerPool 管理 controller 范围的 Informer 实例。
  
  关键性质：
    1. fail soft - informer 启动失败 log warn，既有路径继续工作
       （与 KubectlWatcher 失败处理同谱）
    2. 添加而非嵌入 - 加在既有 6 个 goroutine 之后，顺序不变
    3. 不订阅事件 - cache 自动维护，等 Step 2b/c/d 调用方接入
    4. 不注册 metrics - HTTP server 未实施，留 v2.7.x

  公共 API:
    NewInformerPool(shardMgr, totalShards, kubeconfig)
    pool.Start(ctx, resource, apiVersion)
    pool.Get(resource) - nil 表示未启动 / 失败
    pool.StopAll() - 幂等，多次调用安全
    pool.RegisterMetrics(reg) - 留 v2.7.x 调用
    pool.Size() - debug 用

可测试性设计:

  newInformerFunc 是函数变量（var）而非直接 eventstream.NewInformer
    var newInformerFunc = eventstream.NewInformer
    
  测试中替换为 fake：
    oldFunc := newInformerFunc
    newInformerFunc = func(...) { return &fakeInformer{}, nil }
    defer func() { newInformerFunc = oldFunc }()
    
  与 internal/eventstream/auth.go 的 readTokenFile / readCAFile 同模式。
  避免引入 DryRun 字段污染生产 API（设计 review 中讨论后否决）。

global.go 接入位置:

  在 orphanSweeper 之后，leader election 之前。
  既有 6 个 goroutine 顺序完全不变。
  
  ```go
  // 7. v2.7 Step 2a-2: informer pool（双保险渐进引入）
  informerPool := NewInformerPool(shardMgr, totalShards, kubeconfig)
  informerPool.Start(ctx, "deployments", "apps/v1")
  defer informerPool.StopAll()
  ```

试点资源选择:

  deployments / apps/v1
  
  理由：
    - 是 KubePivot 主要管理的资源
    - 比 namespace 更接近"业务对象"
    - 不与既有 KubectlWatcher（namespace/configmap）重叠
    - v2.9 sizing engine 未来直接用

  ShardSet 桥接：
    NewShardSetAdapter(shardMgr.Shards(), totalShards)
    与 namespace watcher 同样的 namespace hash 过滤
