feat(scheduler): 乾枢 (v3.0) 调度器骨架 — 维度 A bin packing + 双 DP coordinator + PlanWriter

乾枢调度系统首批核心交付。完成了调度器内核与 KubePivot 现有系统的解耦接口定义、
基于 FFD + 二维 keep 回溯的维度 A 装箱求解器、双 DP 协同收敛循环，
以及将调度结果写回 components.yaml 的 GitOps 写入器。

核心用户价值:
  - 调度器通过接口层与 eventstream / metrics / sizing 解耦，不侵入既有 internal 包
  - 维度 A 装箱支持异构节点，归一化 FFD 排序 + 0-1 背包 DP 精确求解
  - coordinator 在装箱失败时自动裁剪未分配 Pod 并重试，上限 5 次
  - PlanWriter 将调度结果写回 configs/components.yaml，遵循原子写入模式
  - 所有核心逻辑通过单测验证，协调器已在单节点真实集群上跑通端到端数据流

  Q-Scheduler.1=A 调度器与 internal 包解耦: 通过 adapter.go 定义 5 个接口
    ✓ PodLister / NodeLister / MetricsProvider / SizingProvider / PlanWriter
    ✓ 调度器内核只依赖接口，不 import 任何 internal 具体实现
    ✓ 与 v2.7 InformerDetector / v2.8 Checker 接口隔离模式一致
    ✓ 可分别注入真实 kubectl adapter 或单测 mock

  Q-Scheduler.2=A Bin Packing 算法: FFD + 0-1 背包 DP
    ✓ FFD 排序采用归一化资源得分 (CPU/NodeMaxCPU + Mem/NodeMaxMem)
    ✓ DP 使用一维滚动数组 + 二维 keep 表回溯，避免路径劫持
    ✓ 离散化粒度: CPU 50m / Memory 64Mi，与 v2.9 sizing 一致
    ✓ 支持异构节点: 每个节点独立 DP，不同容量自动适配

  Q-Scheduler.3=A Coordinator 协同策略: 只裁剪未分配 Pod
    ✓ 第 0 次不做裁剪直接用原始资源装箱
    ✓ 后续迭代每次将未分配 Pod 的 requestCap 下调 10%
    ✓ 调用 SizingProvider.Compute 后取 min(suggestion, cap) 作为实际资源
    ✓ 与 v2.9 "算法谦逊" 哲学一致: 不主动修改已成功分配的 Pod

  Q-Scheduler.4=A PlanWriter: 原子写入 components.yaml
    ✓ 读原文件 → 修改 NodeSelector → 写临时文件 → os.Rename
    ✓ 与 v2.9 deploy_sizing.go 的原子写入模式 100% 一致
    ✓ 不修改用户其他字段 (只补充 nodeSelector)

  Q-Scheduler.5=A Pod 过滤: 仅处理 requests > 0 的 Running Pod
    ✓ BinPack 入口过滤零值 requests 的 Pod
    ✓ 零 requests 是异常数据，调度器不应为其做决策
    ✓ 与 v2.9 sizing 低置信度降级哲学一脉相承

  Q-Scheduler.6=A 精简接口: 每个接口只暴露调度器需要的方法
    ✓ PodLister: ListAllPods (不是 List/ListAll/Get 全暴露)
    ✓ NodeLister: ListAllNodes
    ✓ MetricsProvider: GetPodMetrics + QueryRange
    ✓ SizingProvider: Compute
    ✓ PlanWriter: WriteAssignments
    ✓ 接口污染风险为零

  Q-Scheduler.7=A kubectl adapter 复用 executor 单例:
    ✓ 通过 executor.GetExecutor().Kubectl() 调用，享受并发限制 (sem=5)
    ✓ 与 v2.7 auth.go / v2.8 cosign.go 的 exec 模式一致
    ✓ Pod.requests 从容器 spec.containers[].resources.requests 正确聚合

  Q-Scheduler.8=A 单节点 demo 验证通过后进入多节点:
    ✓ 当前在 orbstack 单节点集群上跑通完整数据流
    ✓ 多节点支持无需改动算法核心，仅需多节点 kubectl adapter
    ✓ 算法内核以节点容量为参数，天然支持异构集群

打脸记录 (基于本次开发的教训):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ✓ 第 1 次: choice 数组重复声明，回溯时 choice 全为 0 导致漏选 Pod
    根因: 代码重构时保留了旧的初始化块，新块又声明了一次
    修复: 只保留一处 choice 初始化

  ✓ 第 2 次: 一维 DP 的 choice/from 回溯被后续物品覆盖 (路径劫持)
    根因: 0-1 背包的经典陷阱——一维数组无法回溯完整选择序列
    修复: 引入二维 keep[i][c] 布尔表，从后向前逆推正确还原

  ✓ 第 3 次: Mock Pod 没有填 Requests 字段，调度结果 assigned=0
    根因: 单测迁移时 Mock 数据只用 Phase 和 Name，忘了 Requests
    修复: 给 Mock Pod 加上合理的 CPU/Memory 请求值

  ✓ 第 4 次: kubectl_adapter 未解析容器 resources.requests
    根因: podJSON 结构体只定义了 Metadata/Spec.NodeName，未定义 Containers
    修复: 扩展 podJSON 结构体，聚合所有容器的 CPU/Memory 请求

  ✓ 第 5 次: Coordinator 中 requestCap 计算了但从未用于约束 sizing 结果
    根因: Compute 签名没有 maxCap 参数，裁剪仅靠 requestCap 无效
    修复: 在 coordinator 侧就近约束: min(sug.Recommended, cap.Value)

  ✓ 第 6 次: 测试节点容量过紧导致即使裁剪也无法收敛
    根因: Mock sizing 返回值 (500m,256Mi) 固定，节点余量 400m 装不下
    修复: 调整测试节点容量为 1100m + 1024Mi，Mock 改为 (300m,128Mi)
