informer_impl.go 核心组件：

  数据结构：
    informerImpl    Informer 接口的标准实现
    subscriberImpl  订阅者句柄（含独立 goroutine + buffer queue）

  公共 API（实施 Informer 接口）：
    NewInformer      工厂函数（参数验证 + 默认值填充）
    Start            启动 watch loop（startOnce 保护 + started 标记）
    Get / List / ListAll  走 cache 的 lock-free 读
    Subscribe        注册事件 handler
    Stats            监控指标快照
    Stop             优雅关闭（stopOnce + 仅在 started 时等 doneCh）

  watch 主循环（runWatchLoop）：
    初始 list -> 进入 watch 循环
    断线 -> 退避 (NextBackoff) -> 重连
    410 Gone -> 清空 RV -> relist
    resync ticker 触发周期性 relist
    ctx cancel / Stop 优雅退出

  doInitialList：
    K8s API list 分页（limit=500 + continue token）
    一次性 PutBulk 写入 cache（避免 N 次 Put 的 O(N^2)）
    设置 resourceVersion 用于 watch 续传

  doWatch：
    单次 watch 长连接
    chunked transfer encoding (服务端) + bufio.Scanner NDJSON (客户端)
    错误分类：context canceled / errStreamGone / 网络错误

  handleWatchLine：
    解析 K8s watch event JSON ({"type":"...","object":{...}})
    增量序列化优化：仅 RV 变化的 MODIFIED 不触发 EventUpdate
    ADDED -> cache.Put + EventAdd
    MODIFIED -> SkeletonChanged 判定 -> cache.Put + EventUpdate
    DELETED -> cache.Delete + EventDelete
    ERROR (code=410) -> errStreamGone

  dispatchToSubscribers：
    ShardSet.Owns(ns) 过滤
    并发派发到所有 subscribers
    inflight buffer queue（subscriberQueueSize=1024）
    慢 handler drop（计入 EventsDropped）

实施过程中暴露的 2 个 bug（已修）：

  Bug 1: Stop() 在未 Start 时等 5s timeout
    根因：startOnce 已用 -> doneCh 会 close
          startOnce 未用过 -> doneCh 永远不 close
          Stop 走 5s timeout 兜底分支，打 WARN 日志
    修复：加 atomic.Bool started 字段
          Start 中 started.Store(true)
          Stop 仅在 started=true 时等 doneCh

  Bug 2: WatchReconnects 计数漏计正常关流
    根因：watch 长连接被服务端主动关闭（K8s API 5-10min 主动关）
          doWatch 返回 nil（无错误）
          原代码仅在 err != nil 时计数，漏计这种场景
          -> Prometheus 监控指标失真
    修复：watchReconnects.Add(1) 移到 if err 之外
          任何 watch 退出（无论原因）都算 reconnect
    工程意义：
          这是真实生产 bug
          测试用例的 SetForceCloseAfter(1) 模拟了 K8s 服务端关流
          边界场景测试设计暴露了生产监控指标问题
