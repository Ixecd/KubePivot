fix(deploy): 修复跨 Chart 硬编码 Release.Name 导致的首次部署失败

问题:
  1. 业务 Chart 的 Deployment 模板中 ServiceAccount、InitContainer host、
     DB_HOST、DB_NAME、ETCD_ENDPOINTS 使用了 {{ .Release.Name }}，
     与 Postgres/etcd Chart 中基于项目名的命名不一致，导致 Pod 因找不到
     ServiceAccount 而无法创建，且 InitContainer 连不上正确的服务地址。
  2. kp deploy 的 rollout 状态检查错误地使用了 plan.Name (demo) 而非
     helm release 名称 (demo-demo)，导致 kubectl rollout status 找不到目标
     Deployment，即使 Pod 已健康运行，部署仍被判定为失败并触发回滚。

修复:
  cmd/kp/deploy.go           新增确保 namespace 存在的幂等创建逻辑
  cmd/kp/multi_deploy.go     修正 rollout 检查使用正确的 release 名称
  internal/scaffold/helm.go  将业务 Chart 的 Deployment 模板中所有
                             {{ .Release.Name }} 替换为静态变量 name

打脸记录:
  ✓ 第 1 次: Postgres 密码硬编码在 StatefulSet 中 → 改为 secretKeyRef
  ✓ 第 2 次: 业务 Chart 重复创建同名 Secret → 删除冗余生成逻辑
  ✓ 第 3 次: DATABASE_URL 硬编码凭证 → 拆分为独立环境变量
  ✓ 第 4 次: values.yaml 包含已废弃的 DATABASE_URL 样例 → 清理
  ✓ 第 5 次: InitContainer 无超时限制 → 加入计数器重试逻辑
  ✓ 第 6 次: Secret 生成中残留无用的 name 参数 → 清理为纯字符串
  ✓ 第 7 次: 遗漏 wait-etcd 的 host 名修改 → 与 wait-postgres 统一使用 name 变量
  ✓ 第 8 次: 业务 Chart Deployment 模板中 app / serviceAccountName /
     DB_HOST / DB_NAME / ETCD_ENDPOINTS 仍残留 {{ .Release.Name }} →
     全部替换为 name 变量
  ✓ 第 9 次: rollout 状态检查使用 plan.Name 而非 release 名称 →
     改为 release 变量

验证:
  ✓ helm template 渲染后所有资源名称一致
  ✓ kp deploy 首次部署成功 (demo 项目，全部 Pod Running)
