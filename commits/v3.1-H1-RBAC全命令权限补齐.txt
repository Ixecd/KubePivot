feat(rbac): v3.1 H1 — 补齐 7 个写命令的 RBAC 权限检查 + teams.yaml 权限体系扩展

v3.0 全系统审计发现 v2.8 RBAC 推进不彻底：mustCheck() 仅在 4 个命令入口接入
(deploy/resume/rollback/down/sandbox/controller-install/controller-uninstall)，
其余 7 个有副作用的写命令未受权限控制。本次补齐所有缺口。并将projectRoot函数改名为Root。

核心价值:
  - 7 个写命令 (migrate/pvc/secret/chaos/promote/supply-chain/sizing) 全接入 mustCheck
  - Permission 枚举从 10 个扩展到 17 个，覆盖所有 CLI 写操作
  - supply-chain / migrate 等无 namespace 的命令用 projectName 作为授权边界
  - IsValid() / AllPermissions() 同步更新，团队配置校验不再遗漏新权限
  - 不破坏向后兼容：无 teams.yaml → 全权限 (Q-B5)，已有配置无需改动

设计核心 (3 个决策点):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  D1. 无 namespace 命令的授权边界: migrate / supply-chain
    问题: migrate 操作数据库, supply-chain 验证镜像, 都没有 --namespace flag
    决策: 用 projectName (project.env 的 PROJECT_NAME 或 filepath.Base(root)) 作为 ns
    理由: 与 deploy 的 namespace fallback 逻辑一致, teams.yaml 的 glob 匹配 project 名
    边界: 这是"项目级授权", 而非"命名空间级授权"
    标注: 如果团队按 projectName 组织 namespace, glob 匹配自然成立
         如果 projectName ≠ namespace, 需要在 teams.yaml 同时声明两个名字

  D2. runSecretSync / runChaosStop 的 namespace 缺省处理
    问题: runSecretSync 的 --namespace 默认 "", runChaosStop 根本没有 --namespace
    决策: 统一 fallback 到 project.env → KUBE_NAMESPACE → "default"
          runChaosStop 补 --namespace flag (与 runChaosInject 对称)
    理由: RBAC 必须有 namespace 才能做 glob 匹配, "" 匹配不了任何规则

  D3. 权限粒度: 7 个独立 Permission vs 复用已有
    决策: 各命令独立 Permission (如 PermSecret ≠ PermDeploy)
    理由: 运维安全原则——能改 Secret 的人不一定能 deploy, 能注入 chaos 的人不一定能 rollback
    权衡: Permission 越多管理越复杂, 但 KubePivot 的 teams.yaml 是白名单模式
          不声明即无权限, 新权限不影响已有配置 (Q-B5 向后兼容)

打脸记录 (本次开发中的教训):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ✓ 第 1 次: make dev 挂了 — 新权限生效, teams.yaml 未授权
    现象: mustCheck 拒绝 "qc@qc.local" 的 supply-chain 权限
    根因: teams.yaml members 只有 alice@x.com, 本地 actor 是 qc@qc.local
    修复: 加 qc@qc.local member + 补 7 个新权限到 permissions

  ✓ 第 2 次: 修了 member 和 permissions, 继续挂
    现象: 同一个 "no-team-match" 错误
    根因: namespaces glob "kp-prod-*" 不匹配 "KubePivot" (projectName)
    教训: RBAC 检查是三维的: actor × permission × namespace
          补 mustCheck 时必须保证三个维度在 teams.yaml 全部匹配
    修复: 加 "*" 到 namespaces (开发环境全通, 生产环境按项目收紧)

  ✓ 第 3 次: supply-chain / migrate 没有 namespace, 犹豫用什么值传 mustCheck
    根因: mustCheck 签名要求三参数 (actor, ns, perm), 但这两个命令没有 ns 概念
    决策: 用 projectName 作为授权边界 (D1)
    反思: 这暴露了 RBAC 模型的一个局限性——"数据库迁移权限"和"K8s namespace"不是同维度
          但 KubePivot 当前授权单元是"团队 × namespace × 权限",
          把 projectName 映射到 namespace 维度是最小变更路径
          v3.2 可以引入 "global permission" (不绑定 namespace) 作为第四维度
